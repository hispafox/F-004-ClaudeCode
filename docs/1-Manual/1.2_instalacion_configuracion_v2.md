**Duración en clase:** 45 minutos · **Sesión 1, submódulo 2**

## La parte mecánica (y dónde tropieza la gente)

Ya tenemos el modelo conceptual del apartado anterior. Ahora toca dejar Claude Code en marcha. Esta es la parte más mecánica del módulo, pero también donde más gente tropieza — y no por la instalación en sí, que es razonablemente simple, sino porque hay tres o cuatro decisiones de configuración que parecen menores pero condicionan todo lo que viene después.

He visto a más de un equipo terminar la sesión 1 con Claude Code instalado y... poco más. *"Sí, ya lo tengo"*. Y al cabo de una semana, abandonado. La razón casi siempre es la misma: no hicieron el `CLAUDE.md` bien, o lo dejaron en blanco, o lo llenaron de ruido. Sin un `CLAUDE.md` decente, Claude Code en tu repo es como un cocinero recién contratado al que no le has dicho ni el menú del día — sabe cocinar, pero en concreto, en *tu* cocina, va perdido.

El objetivo de este apartado no es solo "instalar la herramienta". Es dejarla operativa, autenticada, con un `CLAUDE.md` decente para tu proyecto .NET + Angular, y los settings configurados al nivel correcto. Cuando termine, tienes base para que el módulo 2 (skills) tenga sentido encima.

Voy directo al grano y según vamos avanzando voy señalando los puntos donde la cosa suele fallar.

## Requisitos del entorno

Empezamos por lo que necesitas tener antes de instalar nada.

### Sistema operativo

- **macOS** 13 (Ventura) o superior. Sin sorpresas. La instalación es directa y todas las herramientas funcionan nativamente.
- **Linux** Ubuntu 20.04+, Debian 10+ o equivalente moderno. Con cualquier distro reciente con bash o zsh, vas a estar bien.
- **Windows 10/11** — y aquí hay novedad importante. Hasta principios de 2026, Claude Code en Windows pasaba sí o sí por WSL2 (Linux dentro de Windows). Desde entonces hay instalador nativo que funciona desde PowerShell o CMD directamente. Si Git Bash está instalado, Claude Code lo usa por debajo cuando ejecuta comandos. Si vienes de tutoriales antiguos que mencionan WSL2 como obligatorio, **ignóralos** — es una limitación que ya no aplica.

Una nota sobre WSL en Windows: si tu equipo ya tiene la infraestructura WSL configurada (devs trabajando en proyectos node/python, integración con Docker), puede tener sentido seguir usándola. La instalación nativa es la opción "menos fricción para empezar" pero no la única válida.

### Cuenta de pago

Necesitas una cuenta. La capa gratuita de Claude.ai **no incluye Claude Code**. Esto coge a algunos por sorpresa, así que conviene tenerlo claro antes de la sesión.

Las opciones, ordenadas de menor a mayor:

- **Claude Pro** (20 $/mes) — entry point razonable. Te da Claude Code en tu terminal y Claude.ai en navegador con cuotas diarias decentes. Para devs que vayan a usar Claude Code unas pocas horas al día, basta.
- **Claude Max** (100-200 $/mes según nivel) — cuotas mucho más altas. Si tirás de Claude Code todos los días varias horas, salta a Max en cuanto notes que estás topando límites con frecuencia.
- **Teams / Enterprise** — para equipos. Gestión centralizada, facturación unificada, controles administrativos. Si esto va para un equipo del cliente, lo más probable es que ya estén en uno de estos planes.
- **API por consumo** — pagas por tokens. Útil para automatizaciones (CI/CD, scripts, integraciones) o si tu uso es intermitente.

Una recomendación práctica: **empieza con Pro**. En una semana sabrás si te quedas corto. Saltar de Pro a Max es trivial; haber pagado Max desde el día uno y no aprovecharlo es tirar dinero.

### Node.js (solo si vas por la vía npm)

Node 18 o superior. Node 22 LTS es la recomendación práctica. Si tu Node es viejo, la forma limpia es usar `nvm`:

```bash
# Instalar nvm
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.0/install.sh | bash

# Recargar shell
source ~/.bashrc   # o ~/.zshrc según tu shell

# Instalar y activar Node 22 LTS
nvm install 22
nvm use 22

# Verificar
node --version    # debería decir v22.x.x
npm --version     # cualquier 8+ vale
```

Si vas a usar el instalador nativo (la vía recomendada ahora), **no necesitas Node para nada**. Es un binario autosuficiente. Esto es importante porque te ahorra tener que mantener Node solo para Claude Code en una máquina donde quizá no programas en JavaScript.

## Instalación: dos vías y cuál elegir

Hay dos formas oficiales de instalar Claude Code en 2026. Conviene elegir bien al principio porque cambiar después es engorroso (no imposible, pero un poco rollo).

### Opción A — Native installer (recomendado)

Cero dependencias. Auto-update en background. Es la vía que Anthropic prueba y soporta como primaria desde principios de 2026.

**macOS y Linux:**

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

**Windows (PowerShell o CMD):**

Sigue el script desde [docs.claude.com/en/docs/claude-code/setup](https://docs.claude.com/en/docs/claude-code/setup). En Windows conviene tener Git para Windows instalado — Claude Code lo usa por debajo cuando ejecuta comandos.

El instalador descarga el binario, lo coloca en el PATH y configura los auto-updates. Toma menos de un minuto.

### Opción B — npm (sigue funcionando, ya no es la recomendada)

```bash
npm install -g @anthropic-ai/claude-code
```

¿Cuándo merece la pena la vía npm? Tres casos:

1. **Necesitas pinear una versión concreta**. En CI/CD, normalmente quieres reproducibilidad — la versión que probaste ayer es la que quieres en el pipeline hoy.
2. **Tu equipo estandariza todo en npm**. Si tienes scripts que asumen que las herramientas se instalan vía `npm install`, ser consistente vale la pena.
3. **Quieres incluir Claude Code como dependencia local de un proyecto**. Útil cuando lo usas en hooks de Husky o tareas de package.json.

Para el día a día normal, el native installer da menos problemas y se actualiza solo. La vía npm es legítima pero requiere que tú te ocupes de actualizarla con `npm update -g`.

### Aviso importante: nunca uses `sudo`

Esto es la fuente de errores número uno entre devs principiantes con npm. Si te da un error de permisos al hacer `npm install -g`, **no es señal de que necesites sudo**. Es señal de que tu npm está mal configurado.

`sudo` no es la solución correcta — abre agujeros de seguridad, instala con permisos de root cosas que no deberían tenerlos, y crea problemas que arrastrás durante meses. Si te da `EACCES`:

```bash
# La forma limpia: configurar el prefix de npm en tu home
npm config set prefix '~/.npm-global'

# Añadir el bin de tu home al PATH
export PATH=~/.npm-global/bin:$PATH

# Y guardar esa línea de export en tu ~/.zshrc o ~/.bashrc
echo 'export PATH=~/.npm-global/bin:$PATH' >> ~/.zshrc
source ~/.zshrc
```

Alternativa todavía más limpia: usa `nvm`. Cuando Node se instala vía nvm, vive en tu home y `npm install -g` no necesita permisos de root nunca.

### La decisión, en una línea

Si esta es tu primera instalación, el **native installer**. Solo plantéate npm si tienes una razón concreta para hacerlo (versión específica, CI, ecosistema npm consolidado).

## Verificación

Independientemente de la vía elegida, después de instalar:

```bash
claude --version
```

Debería devolver el número de versión (a fecha de hoy va por la 2.1.x). Si te dice `command not found`:

- **Lo más habitual**: el PATH no tiene el directorio de instalación. Cierra el terminal y abre uno nuevo. La mayoría de veces se resuelve solo.
- **Si persiste**: revisa que el directorio donde se instaló está en tu PATH. Para nvm: `~/.nvm/versions/node/v22.x.x/bin`. Para el native installer: `~/.local/bin` típicamente.

Y la herramienta más útil para diagnosticar problemas:

```bash
claude doctor
```

Ese comando ejecuta diagnósticos del entorno: estado de auth, PATH, configuración, MCP servers conectados. Es la primera parada cuando algo no va bien — antes de buscar en Stack Overflow, antes de preguntar al canal de Slack, antes de reinstalar. La mitad de las veces te dice exactamente qué falla.

## El primer arranque y autenticación

La primera vez que lances `claude` en una terminal, te pide login.

### Login interactivo (lo normal)

```bash
claude
```

Abre el navegador, te lleva a OAuth, autorizas la aplicación y vuelves al terminal con la sesión iniciada. Funciona con Pro, Max, Teams y Enterprise.

Una nota práctica: si trabajas con varias cuentas (personal y de empresa, por ejemplo), la cuenta queda asociada al sistema. Cambiar es fácil pero hay que saberlo:

```bash
claude /logout
claude /login
```

### API key (para CI, scripts, automatización)

Cuando no hay un humano para abrir un navegador:

```bash
export ANTHROPIC_API_KEY=sk-ant-...
```

Configúralo en variables de entorno del sistema o en el secret manager de tu CI. **Nunca** en código que vaya a git. **Nunca** en `CLAUDE.md`. Cuando lo digo en clase parece evidente; lo digo igualmente porque el día menos pensado alguien hace `git push` con una API key dentro.

### Errores típicos del primer arranque

- **"Permission denied" al ejecutar `claude`** — el binario no es ejecutable. `chmod +x` sobre el binario suele resolverlo.
- **"Could not find Claude Code" en Windows después de instalar** — cierra todos los terminales y abre uno nuevo. Windows a veces tarda en recoger cambios de PATH.
- **OAuth se queda colgado** — desactiva bloqueadores de pop-ups y ad-blockers en el navegador donde se abrió.
- **API key no funciona** — verifica que la variable está exportada (`echo $ANTHROPIC_API_KEY` debería mostrarla) y que tu cuenta tiene saldo.

## CLAUDE.md: el fichero más importante del módulo

Si tuviera que quedarme con una sola pieza de configuración para Claude Code, sería esta. El `CLAUDE.md` es **contexto persistente** — lo que el agente lee al empezar cada sesión para entender tu proyecto. Y cambia drásticamente la calidad del output.

Esto es importante: la diferencia entre un dev nuevo en Claude Code que se frustra y uno que cierra triple de tickets que antes **no está en haber aprendido más comandos**. Está, casi siempre, en haber escrito un `CLAUDE.md` decente.

### Qué es y dónde vive

Es un fichero Markdown en la raíz del repo. Va a git. Lo comparte todo el equipo. Cuando lanzas `claude` desde ese directorio, se carga automáticamente al contexto desde el segundo cero.

En proyectos con monorepo o estructura por módulos, puedes tener `CLAUDE.md` adicionales en subdirectorios. Claude los carga jerárquicamente — el de la raíz aplica siempre, el de un subdirectorio se añade cuando trabajas dentro de él. Útil cuando tienes un monorepo donde el frontend Angular y el backend .NET tienen convenciones distintas y quieres especificarlas por separado.

### Qué meter en CLAUDE.md

Lo que tu equipo ya sabe pero un junior nuevo necesitaría saber para no meter la pata. Más concretamente:

**1. Visión general del proyecto** — 3-5 líneas. Qué es, qué hace, qué stack. No te enrolles. *"Aplicación full-stack para gestión de pedidos B2B. Backend en ASP.NET Core 10, frontend Angular 19, base PostgreSQL. Autenticación con Auth0."*

**2. Estructura de carpetas** — para qué sirve cada carpeta principal. No hace falta listar todo el árbol; solo lo que no es obvio. Si tu carpeta `/utils` se llama `/utils`, el agente ya lo deduce. Si tienes una carpeta `/legacy-orders/` que es código que está vivo pero no se toca, eso sí hay que decirlo.

**3. Comandos clave** — cómo se buildea, cómo se testea, cómo se levanta el dev environment, cómo se corre el linter. **Esto es oro**. Sin estos comandos, Claude inventa los que cree que tienes y casi nunca acierta. Si tu equipo tiene un `make dev` que orquesta todo, ponlo. Si usáis un script `./scripts/start-local.sh`, ponlo.

**4. Convenciones de código** — patrones de naming, async/await, manejo de errores, estructura de DTOs, dónde van las inyecciones, cómo se escriben los tests. Aquí puedes meterte un poco más en detalle, pero sin pasarte.

**5. Reglas duras** — *"no toques los ficheros generados en `/generated/`"*, *"este DTO siempre va con esta convención"*, *"los tests usan xUnit + NSubstitute, **nunca** Moq"*. Las cosas que un junior haría mal y que tú tendrías que corregir cada vez. Aquí también van prohibiciones: *"nunca crees migraciones nuevas sin avisar"*, *"no toques `appsettings.Production.json`"*.

### Qué NO meter en CLAUDE.md

Aquí es donde más fallan los equipos. Un `CLAUDE.md` mal calibrado es **peor que no tenerlo**. Las trampas:

**Documentación que cambia mucho.** Si metes la lista de endpoints o el esquema de la base de datos completo, en dos meses está desactualizado y el agente sigue creyéndoselo. Resultado: genera código contra una realidad que ya no existe. He visto un equipo cuyo `CLAUDE.md` documentaba en detalle 40 endpoints. Tres meses después, 12 de esos endpoints habían cambiado, 5 ya no existían, y 8 eran nuevos. Claude Code seguía creyendo que la API era la del `CLAUDE.md`. Cada generación de cliente HTTP era inservible.

**Datos sensibles.** El fichero está en git. Va a producción. Va al portátil de cada dev. Va a quedarse en los logs de tu CI. **No metas claves**, URLs internas que no deban filtrar, credenciales de bases de datos de prueba, ni nada que un commit accidental pueda exponer. Lo digo dos veces porque el día menos pensado alguien lo hace.

**Cosas obvias.** No le digas *"C# es un lenguaje tipado"* ni *"Angular usa TypeScript"*. Estás gastando contexto y dispersando la atención del agente sobre lo que sí importa.

**Listas exhaustivas de todo.** Cuanto más largo el `CLAUDE.md`, peor calibrado. La regla práctica: si el fichero pasa de 200 líneas, replantéatelo. Lo que está dentro tiene que ganarse el sitio.

**Documentación pensada para humanos.** Esto es sutil. El `CLAUDE.md` no es el `README`. No tiene que ser pedagógico, ni tener introducción, ni explicar la motivación del proyecto. Tiene que dar al agente la información mínima útil para trabajar bien en el repo. Frases como *"Este proyecto fue iniciado en 2023 con el objetivo de digitalizar..."* son ruido — al agente le da igual la motivación, solo le importa qué tiene que hacer.

### Anatomía de un buen CLAUDE.md para .NET + Angular

Una estructura que funciona bien:

```markdown
# Proyecto: Pedidos B2B

Aplicación full-stack para gestión de pedidos en cliente mayorista.
Backend ASP.NET Core 10, frontend Angular 19, BBDD PostgreSQL.

## Estructura

- `/src/Api` — proyecto ASP.NET Core con los endpoints REST.
- `/src/Domain` — entidades y lógica de dominio. Sin dependencias externas.
- `/src/Infrastructure` — acceso a datos (EF Core), integraciones externas.
- `/src/Web` — aplicación Angular standalone.
- `/tests` — tests unitarios e integración (xUnit + NSubstitute).
- `/legacy-orders` — código vivo pero no se modifica. Tocar solo si se pide explícitamente.

## Comandos

- `dotnet build` — compilar la solución.
- `dotnet test` — ejecutar todos los tests.
- `dotnet ef migrations add <Nombre>` — crear nueva migración.
- `cd src/Web && npm run dev` — levantar el frontend en :4200.
- `cd src/Web && npm run lint` — linter Angular.
- `./scripts/seed-db.sh` — poblar BBDD local con datos de prueba.

## Convenciones .NET

- Naming: PascalCase para clases y métodos, _camelCase para campos privados.
- Async/await en todo el stack; nunca `.Result` ni `.Wait()`.
- Manejo de errores: `Result<T>` en capa de dominio, `ProblemDetails` en API.
- Tests: xUnit + NSubstitute. **Nunca Moq.**
- DTOs: terminados en `Dto`, en `/src/Api/Contracts/`.

## Convenciones Angular

- Componentes standalone siempre. Nada de `NgModules` nuevos.
- Signals para estado local; SignalStore para estado compartido.
- Reactive Forms con tipado estricto.
- Tests: Karma + Jasmine para unit, Playwright para E2E.

## Reglas duras

- No tocar `/src/Api/Generated/` — es código autogenerado desde OpenAPI.
- DTOs públicos siempre en `/src/Api/Contracts/` con nombres terminados en `Dto`.
- Migraciones: nunca editar una migración ya aplicada en `main`.
- Nunca crear branches con prefijo `release/*` (las gestiona el pipeline).
```

Esto es punto de partida, no destino. Tu equipo va a refinarlo conforme veas qué pifia el agente y qué hace bien. El `CLAUDE.md` es un **fichero vivo**.

### Tres patrones según el tipo de proyecto

No todos los proyectos necesitan el mismo `CLAUDE.md`. Tres casos típicos:

**Greenfield (proyecto nuevo, equipo pequeño).** Empieza minimalista. 30-50 líneas. Solo estructura, comandos, y tres o cuatro reglas duras críticas. Lo vas engordando según el agente vaya cometiendo errores que repites en cada sesión.

**Legacy (proyecto antiguo con muchas convenciones implícitas).** Aquí el `CLAUDE.md` cobra valor porque el agente no puede deducir las convenciones del código (a menudo el código es inconsistente). Más documentación de "qué hacer y qué no". Especialmente las **reglas duras** son críticas — listar las trampas históricas (*"el módulo X parece dead code pero NO se borra, lo usa un cliente concreto vía endpoint legacy"*).

**Monorepo.** `CLAUDE.md` raíz cortito (visión global, comandos comunes) + `CLAUDE.md` específicos por módulo. El específico de `/services/orders/` documenta cómo se hacen las cosas en ese servicio concreto. Claude carga la combinación cuando trabajas en ese subdirectorio.

## AGENTS.md: el estándar cross-tool

Aquí entramos en una pieza que confunde a bastante gente.

`AGENTS.md` es un estándar abierto que han adoptado varias herramientas — Codex, Copilot CLI, Gemini CLI y Claude Code, entre otras. La idea es la misma que `CLAUDE.md`: contexto persistente para el agente. La diferencia es que es **portable entre herramientas**.

### Cuándo usar AGENTS.md

- **Tu equipo solo usa Claude Code.** Quédate con `CLAUDE.md`. No te compliques.
- **Tu equipo usa varias herramientas de IA distintas** — unos con Claude Code, otros con Copilot CLI, otros con Gemini. Aquí `AGENTS.md` tiene sentido como fuente común.
- **Quieres que tu repo sea agnóstico** para el futuro — `AGENTS.md` para el contexto compartido y, si hace falta, un `CLAUDE.md` muy corto solo para lo específico de Claude Code (que en la práctica es poco).

### El error que hay que evitar

Tener ambos ficheros con el mismo contenido. Claude Code lee los dos, encuentra la información duplicada, y empieza a comportarse raro — a veces aplica una versión, a veces otra, a veces mezcla. Si decides usar los dos, que cubran cosas distintas: `AGENTS.md` para lo cross-tool, `CLAUDE.md` para lo que solo aplica a Claude Code (que es muy poco — comandos específicos, slash commands de skills propios, etc.).

Mi recomendación práctica para un equipo .NET + Angular: **empieza con `CLAUDE.md` solo**. Cuando el equipo esté usando Claude Code de forma consistente, evalúa si compensa migrar a `AGENTS.md` para cubrir otras herramientas. La inmensa mayoría de equipos no llegan a necesitarlo.

## .claude/settings.json y los tres scopes

Última pieza grande de configuración. Esta es de las que más tropiezos genera porque hay tres niveles y la gente mezcla.

### Los tres niveles

**1. User (`~/.claude/settings.json`).** Tus preferencias personales. Viajan contigo de proyecto en proyecto. Aquí van cosas como tu modelo preferido por defecto o flags de comportamiento general que aplicas siempre.

**2. Project (`.claude/settings.json` en el repo).** Configuración del equipo. Va a git. Se aplica a todo el que clone el repo. Aquí van permisos del equipo, hooks, configuración de MCP servers compartidos.

**3. Local (`.claude/settings.local.json` en el repo).** Configuración del proyecto pero solo para ti. Va a `.gitignore`. Aquí van overrides personales sobre el proyecto — por ejemplo, tu cuenta de API si es distinta a la del equipo, o flags personales que prefieres aplicar solo cuando tú trabajas en este repo.

### Casos típicos de tropiezo

**Configurar permisos a nivel user que rompen al pasar a otro proyecto.** Te diste permisos amplios para un proyecto sandbox y se te quedaron activos al cambiar al repo del cliente. Resultado: estás dando permisos al agente que no querías. Solución: los permisos amplios casi siempre van a nivel proyecto, no user.

**Configurar permisos a nivel project sin avisar al equipo.** Tú metes en `.claude/settings.json` un permiso que necesitas, lo commiteas, y al resto del equipo le aparece como cambio sin entender de dónde viene. Genera fricción. Si modificas algo que va a git, avisa.

**Esperar que las preferencias locales viajen con el repo.** El `.claude/settings.local.json` está gitignored. Si te lo borras o cambias de máquina, se pierde. Tener esto claro antes de meter nada importante ahí.

**Mezclar configuración entre niveles sin saber qué prevalece.** Hay un orden de precedencia (project > user, local override de tu copia local). Si te encuentras con comportamientos raros, revisa qué nivel tiene qué.

## Permisos: el modelo de seguridad

Esto merece su propia sección porque Claude Code, a diferencia de Copilot, **ejecuta cosas**. El modelo de permisos es real, no decorativo.

### Cómo funciona por defecto

Cuando Claude va a usar una herramienta — leer un fichero, escribir uno, ejecutar un comando — te pide aprobación. Ves qué va a hacer, decides si lo permites una vez, lo permites siempre para ese tipo de operación, o lo bloqueas.

Esto al principio es agotador. Te pasa a hacer veinte aprobaciones mientras instala una librería. Pero es el modelo correcto cuando estás aprendiendo o cuando trabajas en un repo sensible. Te obliga a saber qué está haciendo el agente.

### Cómo aflojarlo: `allow` y `deny`

En `.claude/settings.json` (proyecto) o `~/.claude/settings.json` (user) puedes definir qué herramientas el agente puede usar sin pedir permiso:

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Write",
      "Edit",
      "Bash(npm run *)",
      "Bash(npm test)",
      "Bash(npm install *)",
      "Bash(dotnet build)",
      "Bash(dotnet test *)",
      "Bash(dotnet ef *)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git add *)",
      "Bash(git commit -m *)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force *)",
      "Bash(git push origin main)",
      "Bash(git reset --hard *)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/*)",
      "Write(./production.config.*)"
    ]
  }
}
```

**`allow`** hace que esas operaciones pasen sin aprobación. **`deny`** las bloquea aunque el agente las pida — útil para comandos destructivos que nunca quieres ejecutar accidentalmente.

La granularidad es por patrón. Puedes permitir `Bash(dotnet *)` para que el agente ejecute cualquier subcomando de dotnet sin preguntar, o ser más restrictivo con `Bash(dotnet build)` y `Bash(dotnet test)` por separado.

### Patrones de permisos por tipo de proyecto

Mi recomendación práctica:

**Proyecto sandbox / aprendizaje.** `allow` permisivo (`Read`, `Write`, `Edit`, `Bash(*)` o casi), `deny` mínimo. La idea es no estar aprobando cada cosa.

**Proyecto de cliente / producción.** `allow` restrictivo (solo Read, Edit, y comandos build/test concretos), `deny` con la lista de comandos destructivos típicos. Un día va a intentar hacer algo que no quieres y te alegrarás de tener el `deny`.

**CI / pipeline automatizado.** `allow` específico al pipeline (qué comandos necesita ejecutar y nada más), modo autónomo activado solo en este contexto. Lo veremos en 1.3.

**Tu portátil con repo de cliente.** `allow` y `deny` heredados del proyecto. **Nunca** activas modo autónomo aquí.

### El modo autónomo

```bash
claude --dangerously-skip-permissions
```

Lo que pone el flag en su nombre. Salta todo el sistema de aprobaciones. Útil en dos contextos muy concretos:

- **Sandbox aislado.** Una máquina virtual que no tiene acceso a producción ni a información sensible, y donde el peor escenario es resetearla.
- **CI/CD.** Un pipeline donde el agente ejecuta una tarea acotada (generar tests, ejecutar lint, formatear código) y el entorno está controlado.

Y el contexto donde **nunca** debería usarse:

- Tu portátil de trabajo conectado a producción.
- Cualquier máquina con credenciales de cliente cargadas.
- Sesiones donde el agente puede tener acceso a `.env`, `secrets`, o configuración sensible.

He visto a gente lanzar `--dangerously-skip-permissions` en su portátil "para que vaya más rápido". El día que el agente decide que la mejor forma de resolver un conflicto de merge es `git push --force origin main`, te acuerdas del flag. Y la conversación con el equipo de operaciones esa tarde no es agradable.

## Errores frecuentes del primer día

Lista no exhaustiva de las cosas que más se ven al instalar y configurar Claude Code:

- **Saltarse el `CLAUDE.md`.** El error más común. *"Ya lo escribiré luego"* — y nunca llega ese luego. Sin `CLAUDE.md`, Claude Code es un cocinero sin menú. Hazlo el día 1, aunque sea minimalista. Lo refinas después.
- **Usar `sudo` con npm.** Como dije, ataja problemas a corto plazo y los multiplica a medio plazo. Configura el prefix bien o usa nvm.
- **Configurar permisos a nivel user en vez de proyecto.** Te abre permisos en proyectos donde no quieres. Los permisos del equipo van en `.claude/settings.json`, no en `~/.claude/settings.json`.
- **Activar modo autónomo en máquina con repo de cliente.** Ya lo dije. Lo digo otra vez porque es de los pocos que pueden joder un día entero.
- **Meter cosas que cambian mucho en `CLAUDE.md`.** Lista de endpoints, esquema de BBDD detallado, versiones de dependencias. Se desactualiza y mete ruido.
- **Confundir `CLAUDE.md` con `README.md`.** Son dos documentos para audiencias distintas. El README es para humanos que llegan al repo; el `CLAUDE.md` es para el agente. Tonos distintos, contenidos distintos.
- **No usar `claude doctor` cuando algo falla.** Antes de buscar en internet, lánzalo. Casi siempre te ahorra el viaje.

Tienes Claude Code instalado, autenticado, con un `CLAUDE.md` decente en tu repo de prácticas, y `.claude/settings.json` afinado al nivel correcto. Esto ya es base operativa.

Antes de pasar, hay una prueba rápida que merece la pena. Lanza:

```bash
claude
```

Y pídele algo trivial pero que requiera leer el repo: *"explícame qué hace este proyecto basándote en el código y el CLAUDE.md"*. Mira lo que devuelve.

Si la respuesta refleja lo que has metido en `CLAUDE.md` — los comandos que listaste, las convenciones, las reglas duras — vas bien.

Si parece que se lo está inventando, o si responde de forma genérica (*"este es un proyecto .NET..."*) sin tocar las particularidades de tu repo, revisa el fichero. Posiblemente le falta señal o tiene demasiado ruido. Iteras un par de veces y vuelves a probar. Esa iteración del `CLAUDE.md` es trabajo útil — se lleva al equipo igual que se lleva la herramienta.
