# 1.1 ¿Qué es Claude Code? Arquitectura y filosofía

**Duración en clase:** 30 minutos · **Sesión 1, submódulo 1** · **Versión:** v4

---

## El malentendido del primer día

Hay un patrón que se repite en casi todos los equipos que adoptan Claude Code. Alguien lo instala, lo ejecuta, le pide algo trivial — *"añade un test al método X"* — y se queda mirando la pantalla. Claude Code se pone a leer ficheros. Mira el contexto. Lee otro fichero. Tarda. Cuando responde, devuelve un test, sí, pero también ha tocado un fichero auxiliar y ha sugerido cambiar otro.

La reacción típica: *"esto es Copilot pero más lento y más metomentodo"*. A los tres días, desinstalado.

Y luego está el caso opuesto — menos común pero también real. Un dev que llevaba dos semanas con Claude Code ya en serio vuelve al equipo con una métrica: ha cerrado 18 issues en una sprint donde antes cerraba 6. La diferencia, dice, no es que escriba más rápido. Es que ha dejado de hacer las partes que más tiempo le quitaban — los tests, los DTOs, la documentación, los refactors pequeños — y se centra solo en lo que requiere su criterio. *"He aprendido a delegar"*, lo resume.

Estos dos casos no son personas distintas con habilidades distintas. Son la misma persona en dos momentos. La diferencia entre el día 3 y la semana 2 está en haber entendido **qué tipo de herramienta es Claude Code**. Cuando esa pieza encaja, todo lo demás del curso se asienta solo. Cuando no encaja, da igual que hagas un máster en skills y subagentes — el resultado va a ser frustración.

Por eso este apartado, antes que nada técnico, es conceptual. Te ahorra las dos semanas de fricción.

## El espectro agentic: del autocompletado a la delegación

Antes de hablar de Claude Code conviene ordenar el mapa. Porque en 2026 ya no hay "asistente vs agente" como dos cajas estancas — hay un espectro de delegación, y casi todas las herramientas modernas se pueden colocar en algún punto.

Por un extremo: el autocompletado clásico. Tú escribes, la herramienta sugiere. La iniciativa la llevas tú, completamente. Si no tecleas, no pasa nada. Por el otro extremo: le pasas un objetivo, la herramienta planifica, lee, escribe código, ejecuta tests, itera, y vuelve cuando ha terminado. Tú validas el resultado.

Lo que ha cambiado en los últimos doce meses es que **la mayoría de herramientas comerciales se han movido hacia el extremo agéntico**. GitHub Copilot, que durante años fue sinónimo de autocompletado, hoy ofrece varios modos:

- **Inline completions** — el de toda la vida. Tecleas, completa.
- **Chat** — conversacional dentro del editor.
- **Agent mode** — autónomo dentro del IDE. Edita varios ficheros, ejecuta comandos en el terminal, itera ante errores. Disponible en VS Code, JetBrains y Visual Studio.
- **Cloud agent** — asíncrono. Le asignas un issue de GitHub y mientras tú comes te abre un PR.

Cursor tiene Tab, Chat, Composer y un Agent mode equivalente. Y existen otras herramientas — Claude Code, Aider, Continue, Codex CLI — cada una con su sabor.

Así que la pregunta ya no es *"¿cuál es agéntica?"*. Casi todas lo son, en algún modo. La pregunta interesante es **dónde vive cada una, qué filosofía de contexto usa, y cuándo encaja mejor**. Esa conversación la dejamos para más tarde en este mismo apartado.

### La frase corta sobre Claude Code

Si tuviera que resumir Claude Code en una línea, sería: **un agente que vive en tu terminal y trata tu repo como una caja de herramientas Unix**.

Cada palabra de ahí pesa. *Agente*: planifica y ejecuta, no solo sugiere. *Vive en tu terminal*: no es un plugin de IDE, es un proceso que se compone con todo lo demás de tu shell. *Trata tu repo como caja de herramientas Unix*: sus primitivas son `Read`, `Glob`, `Grep`, `Edit`, `Bash` — herramientas pequeñas que combina según necesite. Y *como caja de herramientas Unix*: te pide un fichero, `CLAUDE.md`, donde tú escribes en texto plano cómo quieres que se comporte en este repo. No índice mágico. Texto.

Esa decisión arquitectónica — terminal-first, primitivas pequeñas, contexto en texto plano — es lo que diferencia a Claude Code más que cualquier benchmark. Y es lo que vamos a ver en detalle.

### Iniciativa delegada: cómo se siente

Imagina la tarea *"añade un endpoint GET para devolver un pedido por ID"* lanzada desde el terminal en la raíz del repo. Claude Code arranca y se pone a trabajar. Lee `OrdersController.cs` para ver la estructura. Ojea `Order.cs` para entender la entidad. Mira los DTOs existentes — *"¿hay un `OrderDto`? Sí, en `/Contracts/Orders/`"*. Comprueba cómo están escritos otros endpoints similares para seguir el patrón. Identifica que necesita el repositorio de pedidos, lo busca. Genera el método del controller. Genera el DTO de respuesta si no existe. Genera el test de integración con `WebApplicationFactory` siguiendo el patrón que ha visto. Ejecuta los tests. Si fallan, los analiza, modifica lo que toque, vuelve a ejecutar. Y al final te dice: *"endpoint añadido, dos ficheros modificados, un fichero nuevo, todos los tests pasan"*.

Tú no has escrito nada. Has descrito una intención y has validado un resultado.

A esto le llamamos **iniciativa delegada**. Tú defines la tarea, el agente decide cómo abordarla. El espacio de decisión que antes era tuyo — qué fichero abrir primero, qué patrón seguir, qué tests escribir, en qué orden hacerlo — pasa a estar dentro del scope del agente.

No es un patrón exclusivo de Claude Code. Lo comparte con Copilot agent mode, con Cursor Agent y con otros. Pero la forma de Claude Code de hacerlo — desde la terminal, con primitivas Unix-like y un `CLAUDE.md` que tú controlas — es la que vamos a aprender en este curso.

### Tres consecuencias prácticas

Hay tres cosas que conviene asimilar antes de tocar nada:

**Primera: Claude Code va a tocar más de lo que te imaginas.** Si le pides un test, puede retocar el método que se testea para hacerlo más testeable. Si le pides un endpoint, puede modificar el DTO, el mapper, el controller y los tests, y de paso añadir una entrada en el `Program.cs` o en la documentación. Al principio asusta. *"Pero yo solo te pedí un endpoint, ¿por qué has tocado el `OrderMapper`?"*. Después se valora — está haciendo trabajo de verdad, no autocompletando líneas. Y cuando lleves dos semanas, te darás cuenta de que esos toques laterales son los que mantienen tu codebase sano.

**Segunda: la conversación cambia de naturaleza.** Si vienes de usar Copilot únicamente como autocompletado en el editor, la transición es grande: pasas de teclear con sugerencias a delegar tareas enteras. La conversación se parece más a la que tendrías con un junior bien preparado al que le pides un favor (*"oye, ¿puedes meterle un endpoint para devolver pedidos por ID?"*) que con un editor mejorado. Esto cambia incluso la forma de redactar las peticiones — más narrativa, menos técnica, más enfocada al objetivo de negocio.

**Tercera: vas a estar menos delante del teclado.** Esto es lo que más cuesta a algunos perfiles. Si tu identidad como dev está construida sobre *"yo escribo el código"*, Claude Code te va a pinchar en algún punto. La adaptación pasa por re-encontrar dónde aportas valor: ya no es tecleando, es decidiendo qué se hace, validando que está bien hecho, y resolviendo lo que el agente no sabe resolver. Que también es código, pero menos.

### Un anti-patrón muy común al empezar

Mucha gente, en la primera semana, intenta usar Claude Code como si fuera un asistente conversacional limitado: *"abre `OrdersController.cs`, busca el método `Get`, ahora añade después de él un nuevo método llamado..."*. Le dictan paso a paso. Lo tratan como una versión voice-to-code de su editor.

Esto funciona, pero es como tener un cocinero profesional y dictarle *"pon un huevo en la sartén, ahora otro, ahora una pizca de sal"*. Has cogido la herramienta más cara del mercado para usarla como una más barata. Si el cocinero no decide nada, ¿para qué pagas a un cocinero?

La señal de que estás usando bien Claude Code es que tus peticiones son **objetivos** (*"que el endpoint devuelva 404 si no existe el pedido"*) y no **recetas** (*"añade un `if` que compruebe si es null"*). Cuando llegues a ese punto, sentirás el cambio de productividad.

## Anatomía interna: cómo está hecho por dentro

Por dentro, Claude Code tiene dos piezas grandes y un puñado de mecanismos auxiliares.

La primera pieza es el **motor** — un modelo de lenguaje grande, Opus o Sonnet según el plan que tengas. Es el que razona, decide y genera código. Sin el motor, no hay agente; solo un script que ejecuta órdenes ciegas. Aquí hay una decisión estratégica importante de Anthropic: el motor de Claude Code es exactamente el mismo modelo que el del chat de Claude.ai, el mismo de la API, el mismo que se usa desde Cursor o desde Copilot cuando el usuario elige Claude. No hay un "Claude Code Mini" entrenado aparte. Esto significa que la calidad del agente sube cada vez que sale un modelo nuevo, sin que tú tengas que hacer nada.

La segunda son las **herramientas integradas**. Las acciones que Claude puede ejecutar dentro de tu sistema:

- `Read` — leer un fichero.
- `Write` — escribir un fichero (creación o sobreescritura completa).
- `Edit` — modificar un trozo concreto de un fichero existente sin reescribirlo entero.
- `Bash` — ejecutar comandos en la terminal.
- `Glob` — buscar ficheros por patrón.
- `Grep` — buscar texto dentro de los ficheros.

Más algunas auxiliares (`WebFetch`, `WebSearch`, `Task`, herramientas de gestión de procesos largos) que entran en juego en casos concretos.

Si te suena Unix, no es casualidad. Esas seis primitivas mapean casi uno-a-uno con `cat`, `>`, `sed`, `bash`, `find` y `grep`. La filosofía es esa: pocas herramientas, bien definidas, que el agente combina según necesite.

### Cómo se combinan en la práctica

El agente combina estas herramientas según lo que necesita. Pero esto suena abstracto, así que veámoslo con una traza concreta:

**Tarea:** *"explícame qué hace este controller"*

El agente ejecutará algo parecido a:

```
1. Read OrdersController.cs                  → lee el fichero
2. Grep "IOrderRepository" en /src/Domain    → busca dónde se define el repositorio
3. Read OrderRepository.cs                   → lee la implementación del repositorio
4. Grep "Order" en /src/Domain/Entities      → busca la entidad
5. Read Order.cs                             → lee la entidad
[... síntesis y respuesta ...]
```

**Tarea:** *"genera tests unitarios para el método CreateOrder"*

```
1. Read OrdersController.cs                  → entiende el método a testear
2. Glob /tests/**/*OrdersControllerTests*    → busca tests existentes (si los hay)
3. Read existing test file                    → ve el patrón usado
4. Read referenced dependencies               → entiende mocks necesarios
5. Write OrdersControllerTests.cs            → genera los tests
6. Bash dotnet test --filter ...              → los ejecuta
[... si fallan, los analiza, los corrige, repite ...]
```

**Tarea:** *"crea un nuevo endpoint para cancelar un pedido"*

```
1. Glob OrdersController.cs                   → localiza
2. Read OrdersController.cs                   → ve patrones existentes
3. Read Order.cs                              → ¿hay método CancelOrder?
4. Grep "CancelOrder" en /src                 → ¿ya existe lógica de cancelación?
5. Read OrderService.cs                       → cómo se gestiona la lógica
6. Edit Order.cs                              → añade método CancelOrder
7. Edit OrderService.cs                       → añade orquestación
8. Edit OrdersController.cs                   → añade endpoint
9. Write OrdersControllerCancelTests.cs      → tests
10. Bash dotnet build                         → comprueba que compila
11. Bash dotnet test                          → ejecuta tests
[... iteración hasta que todo verde ...]
```

Lo importante de estas trazas no es memorizarlas. Es ver cómo el agente **descubre el contexto que necesita** antes de escribir nada. No genera código contra una idea preconcebida — primero entiende, luego actúa.

### La implicación más importante

Cuando le pidas algo a Claude Code, **no le digas qué herramientas usar**. Dile qué quieres conseguir. El agente decide la combinación.

Si tú le dices *"abre `OrdersController.cs` y modifica el método `Get` para que devuelva 404 si no encuentra el pedido"*, lo va a hacer. Pero estás obligándole a usar `Read` y `Edit` cuando él, por su cuenta, hubiera comprobado primero si tu equipo tiene un patrón estándar para 404 (Result<T>? Excepción tipada? `NotFound()` directo?), hubiera buscado cómo lo hacen otros endpoints, y posiblemente hubiera detectado que tu equipo usa `ProblemDetails` y no un simple `NotFound()`.

Cuando dictas las herramientas, te estás llevando la mitad del valor del agente. La señal de que estás haciéndolo bien: tus peticiones describen *resultados*, no *pasos*.

## El ciclo agentic, paso a paso

Aquí es donde la cosa se pone interesante. Cuando le pides algo a Claude Code, no ejecuta una acción y devuelve. Entra en un ciclo de cuatro fases que se repiten hasta terminar la tarea.

### Fase 1 — Lectura de contexto

Claude lee lo que necesita para entender la tarea. No lee todo el repo (eso sería ineficiente y probablemente imposible por contexto). Lee lo relevante.

¿Cómo decide qué es relevante? Combina varias señales:

- El `CLAUDE.md` del proyecto (lo veremos en 1.2) — que le da una visión general del repo.
- La estructura de carpetas que ve con `Glob`.
- Las palabras clave de tu petición — busca con `Grep` los términos que has mencionado.
- Las dependencias que va descubriendo — si lee el controller, ve que importa `IOrderRepository`, y eso le lleva a leer la interfaz.

En tareas pequeñas esta fase dura segundos. En tareas grandes (un refactor cross-fichero) puede llevar varios minutos de exploración. Y aquí es donde algunos devs se ponen nerviosos pensando que la herramienta está rota — *"¿pero por qué está abriendo tantos ficheros?"*. Está construyendo el contexto. Sin ese contexto, lo que escriba después será paja inventada.

### Fase 2 — Razonamiento

Decide cómo abordar la tarea. Qué ficheros tocar, en qué orden, qué comandos ejecutar, qué riesgos hay.

Esta fase no se ve en pantalla; ocurre dentro del modelo. Pero deja huella en lo que hace después. Si el agente, antes de tocar código, te dice algo como *"voy a empezar por modificar el `Order.cs`, después actualizo el servicio, y al final añado el endpoint en el controller"*, eso es razonamiento explícito. A veces lo verbaliza, a veces no.

Hay un comando — `/plan` — que fuerza al agente a hacer esta fase de forma explícita y pedirte aprobación antes de actuar. Lo veremos en 1.3. Para tareas grandes, lanzarlo es la diferencia entre un buen resultado y un *"no, espera, no por ahí"*.

### Fase 3 — Acción

Ejecuta. Modifica ficheros, lanza comandos, escribe código. Aquí es donde sí se ve actividad: los ficheros que toca, los outputs de los tests, los logs.

Esta fase es la que más se parece a la ejecución de cualquier herramienta. Pero hay un matiz importante: el agente no actúa "ciegamente" según un plan rígido. Si en mitad de la acción descubre algo inesperado — *"el `OrderRepository` no tiene método `GetById`, hay que crearlo"* — adapta el plan sin pedirte permiso. Es lo que tiene la iniciativa delegada.

### Fase 4 — Verificación

Aquí es donde Claude Code marca distancia con cualquier herramienta de autocompletado: **comprueba si lo que ha hecho funciona**.

Si ha lanzado tests, lee los resultados. Si fallan, analiza por qué. Si encuentra el error, modifica el código y vuelve a ejecutar. Si no encuentra el error a la primera, sigue investigando — busca en el código, busca en los logs, prueba hipótesis.

El ciclo se repite hasta que el agente considera que la tarea está terminada o hasta que se queda atascado y te pide ayuda. En una tarea pequeña puede haber dos vueltas. En una grande, ocho o diez.

(Nota honesta: Copilot agent mode también verifica e itera. La diferencia no es tener fase de verificación, sino la cultura de uso — Claude Code la pone en el centro desde el primer comando, sin que tengas que cambiar a un modo concreto.)

### Por qué Claude Code parece "lento" al principio

La queja más común de la primera semana. Y es, también, la más malinterpretada.

Le pides un cambio sencillo — *"renombra esta variable"* — y ves que tarda 30 segundos donde un autocompletado habría tardado uno. Tu primera reacción: lento. Pero no está siendo lento. Está iterando. En esos 30 segundos ha leído los ficheros donde aparece la variable, ha verificado dónde se usa, ha hecho el cambio, ha comprobado que el código sigue compilando, y ha asegurado que no se ha roto nada en cascada.

La métrica honesta no es *"cuánto tarda en responder"*. Es *"cuánto tarda el cambio en estar terminado y validado"*. Si Copilot inline te tarda un segundo en sugerir el rename pero después tú dedicas 5 minutos en revisar manualmente que no se ha roto nada en cinco ficheros distintos, has tardado 5 minutos y un segundo. Claude Code ha tardado 30 segundos. Hazte el cálculo.

Lo que pasa es que esos 5 minutos tuyos no los cuentas. Te los cobras como tiempo de calidad. La impresión de "el autocompletado fue rápido" se sostiene porque la verificación la has hecho tú, mentalmente, y no la metes en la ecuación. Claude Code mete la verificación en la ecuación de fábrica. Por eso parece lento. Por eso es más rápido.

## Comparativa con Copilot y Cursor: cuándo cada cuál

Casi seguro que en tu equipo hay gente usando una de las otras dos. Antes o después toca explicar por qué Claude Code es distinto. La trampa es venderlo como *"lo más agéntico"*, porque ya no lo es en exclusiva. Y tampoco es *"lo mismo pero mejor"*. Es **otra arquitectura de producto** con compromisos distintos.

| | Copilot | Cursor | Claude Code |
|---|---|---|---|
| **Dónde vive** | IDE (VS Code, JetBrains, VS) + GitHub | IDE propio (fork de VS Code) | Terminal |
| **Modos disponibles** | Inline, Chat, Agent mode (en IDE), Cloud agent (asíncrono) | Tab, Chat, Composer, Agent | Sesión interactiva, headless (CI), subagents |
| **Modelo** | Multi-vendor configurable (Claude, GPT, Gemini) | Multi-vendor configurable | Anthropic — Opus, Sonnet, Haiku |
| **Filosofía de contexto** | Indexación gestionada por GitHub + memoria opcional | Indexación del workspace | `CLAUDE.md` en texto plano + primitivas Read/Glob/Grep |
| **Integración natural** | GitHub (issues, PRs, Actions, code review) | El editor mismo | Cualquier CLI por composición shell — pipes, scripts, CI |
| **Curva de aprendizaje** | Plana en inline, media en agent mode | Suave | Más vertical — cambia tu forma de trabajar |
| **Coste mental** | Bajo en inline, medio en agent | Medio | Alto al principio, bajo después |

Tres comentarios sobre la tabla, porque la tabla sola se queda corta.

**Sobre "modos".** Copilot y Cursor son herramientas multi-modo: tienen un modo ligero para tecleo asistido y un modo agéntico para tareas grandes. El usuario elige a cada momento. Claude Code es mono-modo: siempre está en delegación. No hay "modo autocompletado" — para eso, ni se enciende.

**Sobre "modelo".** Copilot y Cursor te dejan elegir el modelo (incluso Claude). Claude Code es Anthropic puro. Esto a veces es desventaja (si tu cliente exige un modelo concreto que no es Anthropic), y a veces es ventaja (consistencia: el mismo modelo razonando igual en chat, IDE y terminal).

**Sobre "dónde vive".** Es la diferencia más estructural y la que más impacto tiene en el día a día. Vivir en el terminal significa que Claude Code se compone con cualquier herramienta CLI por pipes, se mete en scripts, se lanza desde CI sin esfuerzo. Vivir en el IDE significa que Copilot y Cursor están donde el dev pasa el día y se integran con todo lo que el editor ya sabe hacer. Son trade-offs distintos. Ninguno es objetivamente superior.

### Escenarios concretos

**Estás escribiendo un método nuevo y sabes exactamente qué quieres escribir.** Copilot inline o Cursor Tab. Te ahorra el tecleo. Lanzar un agente para esto es overkill — y vale para cualquier agente, no solo Claude Code.

**Tienes un fichero feo que quieres limpiar y entender, in-place, mientras lo lees.** Cursor o Copilot Chat. La cercanía del editor compensa.

**Implementar una feature que toca cuatro ficheros y necesita tests.** Cualquier modo agéntico sirve — Claude Code, Copilot agent mode, Cursor Agent. Aquí la elección depende más de dónde te sientes cómodo trabajando que de capacidades.

**Generar 30 tests para un servicio existente.** Igual: cualquier agente. Si vas a lanzar la tarea y volver dentro de un rato, Copilot cloud agent y Claude Code se llevan el premio (los dos despachan tareas mecánicas largas sin supervisión continua).

**Quieres entender un repo que no es tuyo.** Si la sesión es rápida y exploratoria — Cursor o Copilot Chat dentro del editor. Si vas a quedarte trabajando en él durante días — Claude Code, porque le sacas más partido al `CLAUDE.md` persistente y a la composición con scripts.

**Necesitas integrarlo en CI o en automatizaciones.** Aquí Claude Code juega solo. Su modo *headless* (lanzarlo desde un script) está pensado exactamente para eso — pipelines, hooks de Git, generación de docs en cada release. Copilot tiene cloud agent para issues, pero la composabilidad shell la tiene Claude Code.

**Estás haciendo prototipado rápido en un script Python suelto.** Copilot inline. La fricción de cualquier agente — Claude Code o Copilot agent mode — no compensa para algo de 50 líneas.

### La estrategia híbrida que más rinde

La gente que rinde más con Claude Code **no abandona Copilot**. Mantienen las dos.

Copilot — en su modo inline — sigue siendo imbatible para tecleo asistido en el flow del editor. Cuando estás escribiendo un método y sabes exactamente lo que quieres, Copilot te ahorra tecleo. Para eso no hay agente mejor.

Para tareas grandes, hay opciones. Algunos equipos usan Copilot agent mode dentro del IDE porque ya viven ahí. Otros usan Copilot cloud agent para desatender backlog de tickets pequeños. Y los que se llevan mejor con Claude Code suelen ser perfiles que ya viven en la terminal — devs de backend, gente que hace ops o automatización, devs que trabajan multi-repo o multi-stack y no quieren cambiar de IDE entre ellos.

La pregunta no es *"¿agente o autocompletado?"*. Es *"¿qué agente y cuándo?"*. Y la respuesta, sinceramente, depende más de tu flujo de trabajo que de un benchmark.

> Si lo vendes a tu equipo como *"el sustituto de Copilot"*, quien ya está cómodo con Copilot agent mode lo va a comparar feature a feature y va a concluir lo que le interese concluir. La conversación honesta es otra: *"esto vive en la terminal, se compone con todo lo demás del shell, y nos da consistencia con el resto del ecosistema Anthropic — Skills, MCP, subagents. Para nuestro flujo, encaja"*.

### Cuándo NO usar Claude Code

Hay tareas donde Claude Code no es buena opción y conviene saberlo:

- **Edits triviales en un único fichero.** Renombrar una variable local, cambiar un literal de string, ajustar un margen de CSS. Para eso, ve directo y no lances el agente.
- **Trabajo creativo donde tú llevas la inspiración.** Si estás diseñando una arquitectura nueva desde cero y la idea está en tu cabeza, Claude Code puede acelerarte la implementación, pero no le pidas que lleve la dirección — la va a llevar a un lugar genérico.
- **Código que requiere acceso a sistemas que el agente no puede ver.** Si la lógica depende de un sistema externo del que no hay documentación, Claude Code va a inventar (o pedirte detalles continuamente). Mejor escríbelo tú con la doc delante.
- **Tareas donde el coste del error es muy alto y no hay forma de testearlo.** Migración de datos en producción sin entorno de prueba. Modificación de configuración crítica de infraestructura sin staging. Aquí la verificación del agente no compensa el riesgo. Y si lo usas, mínimo en `--plan` sin permitir acción.

## Planes, modelos y costes

Antes de pasar a la instalación, conviene saber qué modelo vas a estar usando, cuánto cuesta y cómo decidir.

### Los modelos disponibles

Claude Code soporta varios. Los relevantes ahora mismo son tres:

**Claude Opus** — el más capaz. Mejor para tareas complejas: refactors grandes, debugging de problemas no triviales, análisis de arquitectura. Más lento y más caro. Si tienes un problema que llevas dos horas dándole vueltas y no sale, es a Opus a quien lo tiras.

**Claude Sonnet** — el caballo de batalla. Suficientemente bueno para el 90% de lo que le vas a pedir, mucho más rápido y barato que Opus. La mayoría de tu día a día con Claude Code va a estar en Sonnet, y está bien que así sea.

**Claude Haiku** — el rápido. Para tareas pequeñas y bien acotadas. No lo recomiendo como default en Claude Code para el día a día — el ahorro no compensa la pérdida de calidad cuando hay razonamiento de por medio. Pero tiene su sitio en automatizaciones donde la tarea es repetitiva y simple.

### Los planes

**Claude Pro** — la entrada razonable. 20 $/mes. Te da acceso a Sonnet y Opus con cuotas diarias y a Claude Code en tu terminal. Para devs que usan Claude Code unas horas al día, suele bastar.

**Claude Max** — 100 a 200 $/mes según nivel. Cuotas mucho más altas. Pensado para quien tira de Claude Code todos los días varias horas. Si llevas un mes con Pro y te encuentras topando los límites con frecuencia, es la señal para subir.

**Teams / Enterprise** — para equipos. Gestión centralizada, facturación unificada, controles administrativos.

**API por consumo** — pagas por tokens. Útil para integrar Claude Code en automatizaciones (CI, scripts) o si tu uso es intermitente y poco predecible.

### Decisión práctica de modelo

Mi recomendación, basada en lo que he visto en equipos:

- **Por defecto, Sonnet.** Hace bien casi todo y tarda la mitad. La inmensa mayoría de tareas se resuelven con Sonnet sin notar diferencia.
- **Cambia a Opus** cuando se cumpla **al menos uno** de estos: (1) Sonnet se ha atascado dos veces seguidas en la misma tarea, (2) la tarea de entrada ya parece compleja (refactor que toca cinco ficheros, debugging de algo raro, análisis de un repo grande que no conoces), (3) es una tarea de criterio (revisar arquitectura, evaluar trade-offs).
- **No cambies cada cinco minutos.** El switch tiene un coste mental — vas a estar pensando *"¿debería estar usando Opus?"* en vez de en la tarea. Decide al empezar la sesión y mantén el modelo a no ser que haya razón fuerte para cambiar. Si vas a alternar mucho, suele significar que estás trabajando en una sesión que mezcla tareas de naturalezas distintas — quizá merece la pena partirla en sesiones separadas.

### Sobre costes y límites

Cada modelo tiene una **ventana máxima de tokens** (en Sonnet ronda los 200k actualmente). Cuando la sesión se acerca al límite, Claude Code empieza a comportarse raro — puede olvidar cosas que dijiste al principio o generar respuestas más superficiales. Hay un comando, `/compact`, que comprime la conversación cuando lo notas. Lo vemos en 1.3 y es de los comandos más rentables que tiene la herramienta.

Para cuotas y límites del plan, el comando `/usage` (o su alias `/cost`) te muestra dónde estás. Hábito útil: lanzarlo cada 20-30 minutos para no llevarte sorpresas a mitad de tarea.

Una idea de magnitud: una tarea típica de tamaño medio (implementar un endpoint con tests) consume del orden de 30-50 mil tokens entre lectura, razonamiento y output. Con Sonnet eso son céntimos. Con Opus, varias veces más. Pero si la tarea hubiera tardado dos horas a un humano, los céntimos siguen siendo gangas.

## Mentalidad: lo que tienes que cambiar para sacarle partido

Esto puede sonar a charla motivacional pero tiene cinco minutos de utilidad real, así que aguanta.

Adoptar Claude Code te obliga a tres cambios pequeños pero reales:

### 1. De "qué tengo que escribir" a "qué quiero conseguir"

La mayoría de devs llevamos años entrenándonos en pensar en código. *"Necesito un método que reciba esto y devuelva aquello, con un try-catch alrededor por si falla la base de datos"*. Esa es la mentalidad correcta cuando tú vas a escribir el método.

Con Claude Code, tienes que dar un paso atrás: *"necesito que el sistema no rompa cuando la base de datos falla, y que el llamante reciba un error tipado para poder reintentarlo"*. La diferencia parece estética. No lo es. La primera te encadena a una implementación concreta. La segunda deja al agente decidir si lo mejor es un try-catch, un Result, una política de retry, o un middleware.

Y aquí viene lo interesante: la decisión que tome puede ser mejor que la tuya. No porque el agente sea más listo que tú — no lo es. Sino porque tiene contexto que tú no estás usando en ese momento. Sabe que tu equipo tiene un middleware de manejo de errores en `Program.cs`. Sabe que en otros endpoints similares no usáis try-catch sino Result. Mientras tú piensas en la línea concreta que ibas a escribir, él lee el repo entero. Cuando le das el objetivo en vez de la implementación, le dejas usar ese contexto.

### 2. De "controlar cada acción" a "validar el resultado"

Esto es lo que más cuesta a los seniors con muchos años de oficio. La mentalidad de control — *"quiero saber exactamente qué está pasando en cada momento"* — es exactamente la que más fricción genera con Claude Code.

El cambio de chip: deja al agente trabajar, y cuando termina, **valida**. Mira el diff. Ejecuta los tests. Comprueba que la solución te encaja. Si no te encaja, díselo (*"no, prefiero que esto se haga con un decorator"*) y deja que reintente. Pero no le dictes paso a paso mientras trabaja — eso anula la mitad de su valor.

### 3. De "lo hago yo" a "delego con criterio"

Esta es la frontera entre seniors junior y seniors senior. Hay tareas que claramente debes delegar (tests, DTOs, migraciones triviales, documentación, refactors mecánicos) y tareas que no (decisiones de arquitectura, código crítico para negocio, performance tunning fino, diseño de APIs públicas).

La curva de aprendizaje real con Claude Code no es técnica — es saber dónde está esa frontera para tu caso. Y esa frontera no se enseña en un curso, ni la encuentras leyendo un blog. Se descubre. La primera vez que delegas algo que deberías haber hecho tú y se rompe en producción, aprendes. La primera vez que haces a mano algo que el agente habría hecho mejor en la mitad de tiempo, también aprendes. Las dos lecciones cuentan. Y las dos vienen de usar la herramienta el suficiente tiempo como para haberte equivocado en ambos sentidos.

## Errores frecuentes del primer día

Una lista no exhaustiva de las cosas que más se ven al empezar:

- **Tratar el agente como un autocompletado.** Le hablas en pasos pequeños. Resultado: te frustras porque "es lento". Cambio: dale objetivos, no recetas.
- **Aprobar todas las acciones a ciegas.** El modelo de permisos existe por algo. En tareas de cliente, párate a leer qué va a hacer antes de aprobar. Sí, es más lento. Pero un día va a hacer algo que no quieres.
- **No mantener `CLAUDE.md` actualizado** y luego quejarse de que el agente "no sabe nuestras convenciones". Lo veremos en 1.2.
- **Lanzar `--dangerously-skip-permissions` en el portátil de trabajo** porque "va más rápido". Es la receta para un día con mala suerte y un `git push --force` no deseado.
- **Pedirle tareas demasiado grandes en una sola sesión.** Si la sesión necesita tocar 20 ficheros y tomar varias decisiones de arquitectura, párte la tarea. Una sesión que se hace muy larga acaba con contexto saturado y resultados mediocres.
- **No usar `/plan` para tareas grandes.** Para algo que va a tocar más de 3-4 ficheros, lanzar `/plan` antes te ahorra muchos retrocesos.
- **Comparar contra Copilot inline en tareas pequeñas.** *"Pero esto Copilot lo hace en un segundo"*. Sí. Y para esas tareas, sigue usando el inline. Claude Code no es para todo.

Si te ves cometiendo varios de estos durante la primera semana — completamente normal. Casi todo el mundo pasa por ahí.

## Antes de seguir

Si has llegado hasta aquí, tienes el modelo conceptual del módulo. Lo que viene es mecánico — instalación, configuración, comandos. Pero antes de pasar, una pregunta que conviene hacerse:

¿Qué tarea concreta de tu día a día sería el primer test honesto para Claude Code? No *"algo que ya sabes hacer y quieres ver si la herramienta lo hace igual"*. Algo que te lleva más tiempo del que debería. Un refactor pendiente. Una suite de tests que no acabas de escribir. Un módulo que entiendes a medias y querrías documentar.

Tener esa tarea en mente mientras configuras Claude Code en el siguiente apartado convierte el ejercicio de "instalar herramienta" en "preparar un experimento real". Y ahí es donde se ve si la cosa funciona o no.
